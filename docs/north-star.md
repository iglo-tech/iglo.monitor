# North star

> **iglo.monitor is the one place a solo founder looks to answer three questions about their apps:
> Is it up? Is it throwing errors? What is it logging?
> It runs as one binary on a small VPS, nothing about it should need a team to operate,
> and an AI agent can do all of it on the owner's behalf.**

Every change should move the product toward that sentence or make the codebase better able to get there.
If a proposal does not help one of the three questions, help connect them, or reduce operating cost, it is out of scope.

The work that implements this direction is tracked as GitHub issues, with one milestone per stage. [The roadmap](roadmap.md) explains how they are organised and how to pick one.

## Who it is for

- A solo founder, indie hacker, or very small team running roughly 1–20 apps (web apps, APIs, workers, side projects).
- One admin. No organizations, teams, roles, invitations, or per-project permissions.
- Comfortable copying a binary to a VPS. Not interested in running Kafka, ClickHouse, Postgres, Redis, or a container fleet.

## What "done" looks like

1. **Uptime.** It does what it does today: scheduled checks, history, notifications, status pages, maintenance windows.
2. **Errors.** An app using the first-party SDK (Bun, Astro, Vue, Alpine.js) or any official Sentry SDK points its DSN at iglo.monitor and gets grouped issues with stack traces, breadcrumbs, tags, regressions, and alerts.
3. **Logs.** The same apps send structured logs (through either SDK, or a plain HTTP endpoint) that can be filtered, searched, and live-tailed.
4. **One view.** A monitor and its app's errors and logs sit side by side. When a monitor goes down, the incident view shows the errors and logs from the same time window. One alert pipeline covers all three signals.
5. **Agent-operable.** Everything above can be done through MCP: setting up monitors and projects, wiring the SDK, triaging issues, searching logs, managing incidents and status pages, and changing settings. The owner chooses per key how much an agent may do.

## Product principles

1. **Uptime is never degraded by ingest.** The monitor scheduler shares a process with error and log ingest. Monitor checks always win: ingest is bounded, queued, and shed under pressure (it returns HTTP 429) before check latency moves. Changes on the ingest path include before/after scheduler-latency measurements.
2. **One protocol, one small SDK.** Errors, logs, cron check-ins, and replays arrive over the Sentry envelope protocol, so every official Sentry SDK works unmodified. The first-party SDK covers only the owner's stack (Bun, Astro, Vue, Alpine.js), speaks the same protocol, and stays tiny. The server never grows an SDK-specific endpoint. A plain JSON/NDJSON log endpoint serves `curl`, Vector, and Fluent Bit.
3. **Bounded by default.** Every table that grows with ingest has an age limit _and_ a hard size cap that are on from day one. Running out of disk is the most likely way a self-hosted observability tool fails. That failure is our bug, not the user's.
4. **Correlation is the product.** Separate uptime, error, and log tools already exist. The reason to use this one is that the three signals share a timeline, a dashboard, and an alert pipeline. Prefer features that connect signals over features that deepen one in isolation.
5. **Small and complete beats big and partial.** Ship a narrow feature that works end to end (ingest → store → UI → alert → retention) before widening any part of it.
6. **One binary, one data directory, SQLite.** No new runtime services, no new database engines, no Docker-only paths. Backups mean copying the data directory.
7. **Readable at 2 a.m.** Prefer clear defaults and a few well-chosen views over configurability. Each screen should answer a question without setup.
8. **Agent parity.** Anything the owner can do in the UI, an agent can do through MCP, through the same code path. A feature is not done until its MCP tool ships. Writes are safe to retry (`request_id`), destructive and public actions can be previewed (`dry_run`), and the owner can always see what an agent did.

## Scale envelope

These are design targets. They decide trade-offs and need to be checked with benchmarks under `docs/perf/`.

| Dimension              | Target                                                                    |
| ---------------------- | ------------------------------------------------------------------------- |
| Host                   | 1 vCPU, 1 GB RAM VPS                                                      |
| Projects               | up to ~50                                                                 |
| Sustained error ingest | ~50 events/s                                                              |
| Sustained log ingest   | ~500 records/s                                                            |
| Bursts                 | ~5k events or records accepted into a bounded queue, the excess gets 429  |
| Default disk budget    | errors 1 GB, logs 5 GB (configurable, enforced)                           |
| Query latency          | issue list and log search on a 7-day window under ~300 ms at the disk cap |
| Monitor check jitter   | no measurable regression while ingest is at the sustained targets         |

Anything that needs much more than this is a non-goal. The answer is a different tool, not a more complex iglo.monitor.

## Non-goals

- Users, organizations, teams, roles, SSO, invitations, compliance-grade audit logs. (A bounded agent activity log is in scope, D15.)
- A general REST admin API. MCP is the machine interface (D14). Plain HTTP stays only where a protocol needs it: ingest, push, badges, metrics, source-map upload.
- Database backends other than SQLite. Columnar or external stores.
- Performance tracing UI, span waterfalls, profiling, release health, crash-free sessions.
- Session replay before stages 0–6 of the roadmap ship, and full-session (rather than on-error) replay at any time (D13).
- Native symbolication (dSYM, PDB, ELF debug files, ProGuard).
- Metrics or time-series ingest beyond what monitors already record.
- SDKs for stacks other than Bun, Astro, Vue, and Alpine.js. Agents or log shippers of our own.
- Hosted, multi-tenant, or SaaS operation.
- Feature parity with Sentry, Better Stack, Rustrak, or Uptime Kuma. Their features are inspiration, not requirements.

## Glossary

- **Project**: one app or service that sends telemetry. It owns one or more DSN keys. It can be linked to monitors.
- **DSN**: the client connection string, `https://<publicKey>@<host>/<projectId>`.
- **Envelope**: the Sentry wire format: a header line followed by items (event, log, attachment, session, and more). We parse the item types we support and ignore the rest.
- **Event**: one error occurrence received from an SDK.
- **Issue**: a group of events that share a fingerprint. It has a status (`unresolved`, `resolved`, `ignored`), first and last seen times, and a count.
- **Regression**: a new event for a `resolved` issue. It reopens the issue and triggers an alert.
- **Log record**: one structured log line, with timestamp, level, message, attributes, and an optional trace id.
- **Signal**: uptime, errors, or logs.
- **Ingest pressure**: the queue fill level. The input to load shedding.
- **Operational incident**: the owner-facing outage record from #82, separate from public status-page incidents.
- **Outbox**: the durable delivery-intent queue from #79. Every alert, from monitors and from telemetry, goes through it.
- **Query / command**: a transport-free service function for one read or one write capability. UI and MCP both call it (D14).
- **Scope**: what an agent key may do (`read`, `write`, `delete`, `publish`, `admin`, D15).
- **Check-in**: a Sentry `check_in` envelope item reporting a cron job's start or result. Mapped onto #86 job runs.

## Guidance for AI agents

1. Read this file, `AGENTS.md`, [the roadmap](roadmap.md), and the GitHub issue you are working on before starting. The issue's acceptance criteria plus the roadmap's default definition of done are the definition of done.
2. Work one issue per branch or PR. Put its ID in the PR title when it has one (`FND-012`, `OBS-105`) and close it from the PR body (`Closes #112`).
3. Respect the stage order: take work from the earliest open milestone, and do not start an issue whose GitHub "blocked by" dependencies are still open. Stage F (Foundation) gates all feature work. Do not build new code on top of untyped code; rewrite what you depend on first.
4. If an issue conflicts with a principle or decision above, stop and comment on the issue. Do not quietly pick one.
5. Keep scope narrow. Write follow-up work down as a new issue in the right milestone, with its blockers set, not as extra code in the current PR.
6. Ingest, storage, and scheduling changes need before/after measurements under `docs/perf/` (principle 1, and `AGENTS.md`).
7. Decisions in this file change only through a PR that edits this file. Record the change in the decisions table.
